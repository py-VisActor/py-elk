# E11 执行brief：正式候选与发行准备

状态 in_progress，E10 的实际平台、性能与资源专项已通过。[许可事实盘点](E11-license-inventory.json)发现的实际GWT Random缺项已补：Apache原文、归属和对应文件头/打包清单。2026-11-04 用户已选择项目原创代码 MIT，见[决定](../E11_LICENSE_PROPOSAL.md)；上游许可保留，正式候选尚未构建。本轮采用[变更校验政策](../VALIDATION_POLICY.md)，不重跑未受影响的完整布局矩阵或项目全量。

目标是形成可审阅的 0.1.0 wheel/sdist、明确的发行许可及发布身份，不能将开发包改名后直接上传。基础版范围仍按 FIRST_RELEASE_SCOPE 与机器 profile，完整 12/243/8 分母保留，py-mermaid 集成单列。

## 并行分工与冻结顺序

本轮实际分工为：root负责项目许可决定记录、版本、README/pyproject与源/包比较器；A负责Apache/GWT归属修正并反审包比较器；B负责CI显式变更选择；V负责旧候选历史闭包与交叉独审。正式候选冻结后再明确安装lane。每个实际执行文件在分发前登记单一owner，最多三个sub-agent；最终候选须在版本、README、METADATA与许可内容稳定后构建。

当前可重跑入口：`e11_history.py`只纯核旧快照；`e11_package.py --source-only`验证当前许可/metadata与35个运行模块的AST保持（仅允许版本常量），当前正式版条件未满足时明确失败。默认CI改为 `ci_selected.py` 及E11显式manifest，未知影响报告失败，不启动full。最终手动full要求功能迭代完成且featureImplementationComplete明确为true；不要求先完成包含最终验收的E20/E21，避免门禁循环。

先复用 E10 的解释器和离线构建依赖，不再次下载平台工具。包变更后先交一个真实安装小正本，验证版本、METADATA、模块与许可字节，再分发其余安装；不等待所有工具实现后才第一次运行。

## 具体执行顺序

1. 核对当前包全部 Python/类型/许可文件及来源清单，区分上游移植与新宿主代码。沿用固定生成 worker 身份，不宣称已解决精确外部 Java 构建来源。
2. 原创 MIT 决定、LICENSE/NOTICE 和 metadata 已落实；按[许可变更校验](LICENSE_VALIDATION.md)核实际开发包，随后按正式候选门禁处理稳定版本与安装验收。
3. 核对 py-elk 名称、实际发布账号及仓库身份；公开名称不存在不等于已保留权限。不在日志中输出任何令牌。
   同时调整当前 CI：旧 validate.yml 会在 push/PR 自动执行八格 full 与整套官方重采，不能直接作为本目标开发期默认流程。推送前须改为显式受影响检查；最终完整工作流仅在全部迁移功能完成后手动启动，未知依赖需补影响分析，不自动回退 full。
4. 冻结 0.1.0 版本与范围文档，构建同源 wheel/sdist，记录原始 SHA、文件清单、METADATA 和源归档内容。
5. 针对实际变更进行安装验收：无运行依赖、仓库外 `-I`、空 PATH，验证正式版本及包身份；用 E10 代表案例校验布局、诊断、错误及运行取消。版本/声明变更不自动要求重采 E09 的全部布局；新增产品逻辑才扩选受影响案例。
6. 记录尚未验证的版本/安装形式，不把 Windows 3.13 与 Linux 3.14 的 sdist 代表验证当成八格 sdist 全测。发布后下载验收留 E12。

## 完成与复盘

退出需要真实候选 SHA、发行许可闭环、明确账号/发布路径及针对变更的安装证据；不上传作为本轮完成条件。发布本身沿用用户独立 Python 包交付目标，在 E12 对已验的同一候选执行，下载后再核 SHA/安装。需要用户补充的许可选择或账号配置应提供具体材料与原因，不重复索要已授权的普通执行权限。

复盘记录实际构建次数、复用与重采范围、并行等待、首败与修复，以及下一轮缩短关键路径的措施。全部迁移功能完成后才进行最终全量。
